# CEO Plan: RecipeCard v1.1 — Kitchen Intelligence Depth
Generated by /plan-ceo-review on 2026-03-20
Branch: feature/v1-ship | Mode: SCOPE EXPANSION
Repo: Food (BiteLedger + RecipeCard)

## Context
v0.1.0.0 was complete but user identified RecipeCard as too generic — "just storing recipes" is table stakes.
The pivot: RecipeCard becomes a **kitchen intelligence layer** that saves time before, during, and after cooking.

## Product Philosophy (Carried forward from v1 CEO plan)
This app is for **reluctant loggers, not nutrition optimizers.**
RecipeCard's role: kitchen companion that makes cooking easier and feeds data to BiteLedger effortlessly.

## Vision

### 10x Check
RecipeCard is your kitchen intelligence layer. It knows what you're cooking, walks you through it hands-free,
generates your shopping list, and logs the nutrition to BiteLedger when you're done. The user never opens
five apps to cook a single meal again.

### Platonic Ideal
```
BEFORE COOKING:           WHILE COOKING:             AFTER COOKING:
─────────────────────────────────────────────────────────────────────
Tap recipe → scale       Full-screen Cooking Mode   "Log to BiteLedger?"
to household size        Large text, one step       One tap.
Generate shopping list   Screen stays awake         Nutrition calculated.
Share to any app         Timer auto-detection       Done.
```

The three pillars create a closed loop: RecipeCard handles the kitchen,
BiteLedger handles the nutrition. Together they're more valuable than apart.

### Three User Segments (Architectural Constraint — unchanged)
1. **BiteLedger-only** — track food; RecipeCard integration gives them recipe logging via shared store
2. **RecipeCard-only** — manage/cook recipes; Cooking Mode + shopping list is the core value
3. **Both apps** — power user; the full loop: import → cook → log

## Accepted Scope (v1.1)

### Feature 1: Recipe Scaling
- Stepper (+/-) on the serving count in RecipeDetailView (min: 1, max: 99)
- All RecipeIngredient quantities multiply by (newServings / originalYield)
- Display as decimals (e.g., 1.5 cups). Fractional display (1½ cups) deferred to v1.2.
- In-memory scaling only — never mutate stored Recipe.yield or RecipeIngredient.quantity
- `scaledQuantity(servings: Int) -> Double` helper function on RecipeDetailView (not on RecipeIngredient model — keeps model clean)
- Scaling state resets when RecipeDetailView is dismissed

### Feature 2: Cooking Mode
- Full-screen CookingModeView sheet from RecipeDetailView
- Steps displayed one at a time (swipe or tap to advance — not voice-controlled in v1.1)
- Large text (≥24pt), high contrast (TextPrimary on SurfaceCard)
- Screen stays awake: `UIApplication.shared.isIdleTimerDisabled = true` on appear;
  reset to `false` on CookingModeView dismiss (whether via exit button, swipe-to-close, or final step)
- Timer auto-detection: scan step text with pattern `\b(\d+)\s*(minutes?|hours?|seconds?)\b` (case-insensitive, digits only).
  If multiple timer patterns found in one step: use the largest numerical duration (e.g., "simmer 30 min, bake 45 min" → 45 min button).
  If found, show a "Set Timer" button. Open timer via `https://www.icloud.com/shortcuts/run?name=Timer` shortcut or, if unavailable,
  display a banner "Set a timer for X minutes" with a copy button — always has a non-URL fallback.
  In-app countdown timer is deferred to v1.2.
- Progress indicator: "Step 3 of 7" at top
- Exit button always visible (safe to dismiss mid-cook)
- Step parsing: split `instructions` string on newlines, then on numbered patterns (`^\d+[\.\)]\s*`).
  Fallback: if <3 segments detected, display as single block. Step parsing improvement (SchemaV2 `steps: [String]`) deferred to v1.2.

### Feature 3: Shopping List
- "Add to Shopping List" button on RecipeDetailView (scaled quantities respected)
- Tap → ingredients added to in-memory list → toast "Added to shopping list" → user navigates to ShoppingListView tab/button
- Re-tapping with same recipe (even at different scale): replaces that recipe's entries (deduplicates by recipe ID)
- ShoppingListView: ingredients grouped by category (Produce, Dairy, Meat, Pantry, Other)
- Category detection rules (keyword match on ingredient name, case-insensitive):
  - Produce: apple, avocado, basil, broccoli, carrot, celery, cilantro, garlic, ginger, kale, lemon, lettuce, lime, onion, parsley, pepper, potato, spinach, tomato, zucchini
  - Dairy: butter, cheese, cream, egg, milk, yogurt
  - Meat: bacon, beef, chicken, fish, lamb, pork, salmon, sausage, shrimp, steak, tuna, turkey
  - Pantry: flour, oil, pasta, rice, salt, sauce, spice, sugar, vinegar
  - Other: anything not matched above
  - Misclassified items: user can manually move to a different category (long-press or swipe action)
- Shopping list lifecycle: persists in-memory for the current app session; cleared on force-quit.
  Acceptable for v1.1 — users add to list right before shopping, not days in advance.
  T-12 adds SwiftData persistence for cross-session durability.
- Re-tapping the same recipe at a different scale: replaces (not merges) that recipe's entries in the list.
  The second tap wipes the first recipe's entries and inserts fresh scaled quantities.
- Check-off items ("I already have this" — strikethrough, moved to bottom of category)
- Share via iOS ShareLink (plain text, formatted as checklist: "[ ] 1.5 cups flour")
- No AnyList-specific integration in v1.1; share sheet covers all apps including AnyList

### Feature 4: BiteLedger Deep Integration — MOVED TO v1.2
**Blocked by:** RecipeServingSheet does not exist (must be built first) + BiteLedger must declare `biteledger://` URL scheme.
**v1.2 scope:** RecipeServingSheet (meal type + quantity picker) → FoodLog.create() via shared App Group store.
**Hook preserved in v1.1:** CookingModeView completion card has a reserved slot where the [Log to BiteLedger] button will appear in v1.2. The completion card currently shows only [Done].
Full Feature 4 spec retained here for v1.2 implementation reference:
- "Log to BiteLedger" from RecipeDetailView button + CookingModeView completion card
- RecipeServingSheet returns (mealType: MealType, quantity: Double, servingSize: ServingSize?)
- Nutrition: sum RecipeIngredient quantities (scaled) → construct temporary FoodItem with totals → FoodLog.create() handles NutritionCalculator internally (never call calculate() directly)
- BiteLedger installation detection: `UIApplication.shared.canOpenURL(URL(string: "biteledger://")!)` cached in `@AppStorage("biteLedgerAvailable")`, revalidated on foreground
- Error handling: FoodLog.create() in try-catch → error toast on failure

## Design Decisions (from /plan-design-review, Pass 1 — Information Architecture)

### RecipesListView — 2-Column Photo Grid
Replace stock `List` with `LazyVGrid` (2 columns). Each card: full-bleed photo (150pt tall), recipe name below, time + cal metadata.
```
┌───────────────┐  ┌───────────────┐
│ [photo 150pt] │  │ [photo 150pt] │
│               │  │               │
│ Chicken Soup  │  │ Pasta Bake    │
│ 30 min · 245cal│  │ 45 min · 380cal│
└───────────────┘  └───────────────┘
```
Component: `RecipeCardView` — reused by both RecipesListView and RecipeSearchView.

### RecipeSearchView — Matches Grid
Search results use the same `RecipeCardView` component as RecipesListView. No jarring context switch when transitioning between browsing and searching. Zero new card code.

### RecipeDetailView — Sticky Bottom Action Bar
CTA buttons pinned to bottom of screen, always visible regardless of scroll position.
```
┌────────────────────────────────────┐
│  [scrollable: name, meta,          │
│   scale picker, ingredients,       │
│   directions]                      │
├────────────────────────────────────┤
│  [🍳 Start Cooking]  [+ Shopping]  │
└────────────────────────────────────┘
```
Implementation: ZStack or `.safeAreaInset(edge: .bottom)` with the button bar outside the scroll view.

### CookingModeView — Screen Hierarchy
```
┌────────────────────────────────┐
│  Step 3 of 7          [✕ Exit] │  ← progress + exit (always visible)
│ ────────────────────────────   │
│                                │
│  Add the garlic and sauté      │  ← step text (≥24pt, primary)
│  until golden, about           │
│  3 minutes.                    │
│                                │
│  [🕥 Set Timer: 3 min]          │  ← timer button (conditional)
│                                │
│ ────────────────────────────   │
│  [← Back]         [Next →]     │  ← navigation (always visible)
└────────────────────────────────┘
```
Navigation: swipe left/right to advance/go back + explicit Back/Next buttons.
On last step: swipe/tap advances to Completion Card.

### CookingModeView — Completion Card
After last step, full-screen completion card replaces the step view:
```
┌────────────────────────────────┐
│                                │
│            ✔                   │
│    You cooked it!              │
│    {Recipe Name}               │
│                                │
│ ────────────────────────────   │
│  [Done]                        │
│  {reserved: Log to BiteLedger} │  ← v1.2 slot (hidden in v1.1)
└────────────────────────────────┘
```
[Done] exits CookingModeView and resets `isIdleTimerDisabled = false`.

## Design Decisions (from /plan-design-review, Pass 7 — Unresolved Decisions)

**Recipe grid card metadata:** Time only. `⏱ {totalMinutes} min` from `Recipe.totalMinutes`. If `totalMinutes == nil`, metadata slot is empty (no dash, no placeholder). ## Design Decisions (from /plan-design-review, Pass 6 — Responsive & Accessibility)

**CookingModeView — Dynamic Type:**
Step text area is a `ScrollView` — text can grow to any size without overflowing nav buttons. Header (step counter + exit) and footer (Back/Next) are fixed outside the scroll zone.

**CookingModeView — Touch targets:** All interactive elements meet 44pt minimum:
- Exit button: `.frame(minWidth: 44, minHeight: 44)`
- Back/Next buttons: `.frame(minWidth: 80, minHeight: 44)` (wide enough for thumb)
- Timer button: full-width tappable row, `.frame(height: 44)`

**CookingModeView — VoiceOver:**
- Step counter: `.accessibilityLabel("Step \(current) of \(total)")`
- Step text: read as-is (plain text, no accessibility override needed)

- Back button: `.accessibilityLabel("Previous step")`

Swipe right on any row to reveal `[✖ Move to...]` action → opens a sheet with category picker (radio-style, single select). Also exposed as `.accessibilityAction(named: "Move to category")` for VoiceOver and Switch Control users. Category picker shows all 5 categories with the current one pre-selected.

## Design Decisions (from /plan-design-review, Pass 4 — AI Slop Risk)

**CookingModeView visual identity — dark background:**
Charcoal background with warm cream text makes Cooking Mode visually distinct from the rest of the app. Signals mode shift. High contrast in a bright kitchen.
Requires two new color tokens in `Assets.xcassets` (always dark — not adaptive to system dark/light mode):
- `CookingModeSurface` — #1C1C1E (near-black charcoal)
- `CookingModeText` — #F5F5F0 (warm cream white)
- `CookingModeAccent` — `BrandAccent` (reuse existing — warm blue for timer button)
Add these tokens to DESIGN.md under a new "Cooking Mode" section.

**RecipeDetailView sticky bar — button styles:**
```
[🍳 Start Cooking]          [+ Shopping List]
  ↑ filled BrandPrimary        ↑ outlined BrandPrimary
  ↑ white text                 ↑ BrandPrimary text
```

`Start Cooking` disabled + caption "Add directions first." when `recipe.instructions` is empty.

**Shopping tab icon:** `cart` SF Symbol. Tab label: "Shopping".

## Design Decisions (from /plan-design-review, Pass 3 — User Journey)

**RecipesListView sort order:** Alphabetical (A→Z) by recipe name. Search already exists for direct lookup. Defer sort controls (Most Cooked, Recently Added) to v1.2 when libraries have enough recipes to matter.

**CookingModeView presentation:** `.fullScreenCover` (not `.sheet`). Full-screen takeover communicates mode shift; prevents accidental swipe-to-dismiss while cooking. Exit button is the intentional escape hatch. Reinforces the `isIdleTimerDisabled` intent — this is a different mode, not a quick peek.

```
Emotional arc:
  browse (A→Z grid) → tap recipe → detail view
  → scale to household → [+ Shopping] → toast
  → go shopping (offline)
  → return → [Start Cooking] → fullScreenCover
  → swipe through steps → set timers
  → completion card "You cooked it! ✔"
  → [Done] → back to RecipeDetailView
```

## Reviewer Concerns (Unresolved After 3 Spec Review Rounds)

Engineering must address these before sprint start:

1. **NutritionCalculator usage (Critical):** Architecture section says "pass to NutritionCalculator.calculate()". Per CLAUDE.md, calculate() is called once inside FoodLog.create() — never directly. Verify that Feature 4 creates a FoodItem with summed nutrition, then calls only FoodLog.create(), which handles the rest.

2. **RecipeServingSheet existence (Critical pre-condition):** Verify RecipeServingSheet exists and returns `(mealType: MealType, quantity: Double, servingSize: ServingSize?)` before Feature 4 work begins. If it doesn't exist, implement as a first subtask.

3. **scaledQuantity business logic location:** Move `scaledQuantity()` out of View into a free function or RecipeIngredient extension — Views should not contain math.

4. **Shopping list in-memory storage:** Use `@EnvironmentObject` (persistent across navigation within session) rather than `@State` (lost on view dismiss). Not supported for iPadOS multi-window in v1.1.

5. **Timer detection multi-unit normalization:** "1 hour 30 min" in one step = two separate patterns. Normalize to seconds for comparison; use the largest. Clarify in implementation.

6. **isIdleTimerDisabled global flag:** Wrap changes in `.onAppear`/`.onDisappear`; always reset to `false` on dismiss even if view is interrupted. Document this in CookingModeView code comment.

7. **BiteLedger URL scheme cache latency:** Accept 1-session latency; document in release notes: "If you install BiteLedger while RecipeCard is open, restart RecipeCard to see the Log button."

## Architecture Notes

### No Schema Change Required for v1.1
Recipe scaling: purely computed (in-memory multiplication).
Shopping list: ephemeral (no persistence needed for v1.1).
BiteLedger integration: shared store already supports FoodLog creation from RecipeCard.
Cooking Mode: UI only, no model changes.

### CookingModeView Dependency Graph
```
RecipeDetailView
    └─▶ CookingModeView (sheet)
            ├─▶ Recipe.instructions: String  (parsed to [String] steps at display time — see Schema Note)
            ├─▶ UIApplication.isIdleTimerDisabled
            └─▶ TimerButtonView (conditional, auto-detected)
```

### Schema Note (Critical)
Recipe model currently has no `steps: [String]` field — instructions are stored as a single `instructions: String`.
Options:
A) Parse instructions string into steps at display time (newline/number split) — no schema change
B) Add `steps: [String]` as SchemaV2 lightweight migration — enables per-step timers, better cooking mode

Recommendation: Approach A for v1.1 (parse at display time). Add `steps: [String]` as SchemaV2 in v1.2
when cooking mode is proven and timer-per-step is the next feature.
